# Enable verification email delivery

## Player flow

Continue as guest to play immediately, or create/sign into a username/password account. Open Profile → Account, enter an email address and select Send code. Enter the six-digit code from the email to unlock all six cities and Map Studio. Verification persists across sign-in and server restarts. Room participants can join the host's chosen map without verifying themselves.

Codes expire after 15 minutes and permit five attempts. Resending is allowed after one minute; a successful resend replaces the previous code. A code can be consumed once. A delivery failure creates no new challenge. Only salted code digests are stored; other players cannot see account email addresses. This flow does not implement password recovery.

## Production setup

1. Create a Resend account and add a domain or subdomain you control, for example `accounts.your-domain.com`. The Railway `up.railway.app` hostname is not a sending domain you control.
2. Copy the exact DNS records generated by Resend to your DNS provider and wait for the domain's verified status. Follow [Resend's domain setup](https://resend.com/docs/add-a-domain); do not guess DNS values. Add DMARC as described there.
3. Create a sending API key in Resend, scoped to the verified domain where possible.
4. In Railway's **spin-the-block → production → Variables**, add:

   | Variable | Value |
   | --- | --- |
   | `RESEND_API_KEY` | The private Resend sending key |
   | `EMAIL_FROM` | `Spin the Block <play@accounts.your-domain.com>` using your actual verified domain |

5. Apply the variables and let Railway redeploy. Keep `DATA_DIR=/data` and the existing persistent volume for account and verification storage.
6. Reload the app or sign in again to refresh email availability. The Send code button becomes available when both variables are configured.

Do not paste the API key into chat, commit it, or expose it in client environment variables. No SMTP server, GitHub secret, webhook, or application public URL is required for this code-based flow. Variable presence enables sending attempts; it does not prove provider authentication or inbox delivery.

## Safe configuration check

Run `npm run email:check` inside the deployed Railway service shell. It reports missing variable names without printing their values or sending mail. `railway run npm run email:check` can also check linked service variables locally; it does not prove the running deployment has applied them. A missing value exits with status 1. Whitespace-only values count as missing.

## Live acceptance check

Use a fresh account and an inbox you control. Request a code, confirm receipt, verify it, then host an extra city and save a custom map. Sign out and back in to confirm the unlock persists. Verify that guest play still works. Never use a production bypass or a fabricated code.

If the app reports delivery unavailable, check both variables and redeployment. If sending fails, inspect Resend's email logs for invalid credentials, domain status, sender mismatch, or quota/rate limits; provider errors are intentionally hidden from players. If Resend accepts the email but it does not arrive, check recipient spelling, spam and the provider delivery/bounce status. The app's “Code sent” means provider acceptance, not guaranteed inbox delivery.
